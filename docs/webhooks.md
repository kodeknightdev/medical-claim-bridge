# Webhooks

Practice management systems want to know when a claim changes without polling. Each provider organisation can
register HTTPS endpoints in the portal (Integrations) or through `POST /api/webhooks`; claim-bridge then sends a
signed JSON request for every subscribed event.

## Events

| Event | Sent when | Data |
|---|---|---|
| `claim.accepted` | the payer accepted the claim (sync ack, 277CA) | claim id and number, payer, status |
| `claim.rejected` | the payer rejected it (999 or 277CA rejection, API rejection) | as above plus the reason |
| `claim.paid` | the claim was adjudicated as paid or partially paid | amounts: charge, paid, patient responsibility |
| `claim.denied` | the claim was denied | denial category and CARC |
| `remittance.posted` | a payment was posted from an 835 | remittance id, charge, paid, allowed, patient responsibility |

[`WebhookEvents`](../src/services/notifications/ClaimBridge.Notifications/Webhooks/WebhookEvents.cs) maps internal
events to this public vocabulary. Payloads carry claim ids, numbers and amounts only; never patient names, member ids
or dates of birth. A receiver that needs more calls the API with its own client credentials.

```json
{
  "id": "6f0c3c55-4e0b-4bb5-9d0f-0d2f6c1f8a11",
  "type": "claim.paid",
  "createdAt": "2025-11-03T14:12:09+00:00",
  "data": {
    "claimId": "d1c1b6b4-6c8a-4a53-a0e8-7b0b8a0f43e2",
    "claimNumber": "CB250100231",
    "payerId": "PAYER-A",
    "status": "Paid",
    "totalCharge": 120.00,
    "paidAmount": 82.50,
    "patientResponsibility": 25.00
  }
}
```

`id` is the delivery id. It stays the same across retries of the same delivery, so receivers should use it to drop
duplicates.

## Signatures

Every attempt carries three headers:

| Header | Value |
|---|---|
| `X-ClaimBridge-Signature` | `t=<unix seconds>,v1=<hex HMAC-SHA256>` |
| `X-ClaimBridge-Event` | the event type |
| `X-ClaimBridge-Delivery` | the delivery id |

The signature is `HMAC-SHA256(secret, "{t}.{raw body}")`
([`WebhookSignature`](../src/shared/ClaimBridge.Contracts/Webhooks/WebhookSignature.cs)). Signing the timestamp
together with the body means a captured request cannot be replayed later: receivers reject anything older than five
minutes. Each retry is signed afresh with a new timestamp.

To verify:

1. Read the raw body as bytes before any JSON parsing.
2. Split the header on `,` and take `t` and every `v1`.
3. Reject if `|now - t|` is more than 300 seconds.
4. Compute the HMAC over `"{t}.{body}"` with your secret and compare it to each `v1` in constant time.

[`verify_signature.py`](../tools/webhook-receiver/ClaimBridge.WebhookReceiver/verify_signature.py) is a standalone
Python version, and the [webhook-receiver](../tools/webhook-receiver/ClaimBridge.WebhookReceiver/Program.cs) tool is a
working .NET receiver used by the demo stack and the e2e tests (`GET /webhooks` lists what it received and whether
each signature was valid).

## Secrets

The signing secret is generated by providers (24 random bytes as hex, prefixed `whsec_`), shown once in the create or
rotate response, and stored encrypted with the PHI protector. `POST /api/webhooks/{id}/rotate-secret` issues a new
one immediately. Because the verifier accepts several `v1` values, a receiver can check against both its old and new
secret while it switches over.

## Delivery and retries

[`NotificationEventsHandler`](../src/services/notifications/ClaimBridge.Notifications/Consumers/NotificationEventsHandler.cs)
turns `claims.status-changed` and `remittance.payment-posted` into one `WebhookDelivery` row per matching
subscription. Creating the rows is the only thing the Kafka consumer does, so a slow receiver never holds up the topic.
[`WebhookDispatcher`](../src/services/notifications/ClaimBridge.Notifications/Webhooks/WebhookDispatcher.cs) picks
due rows every two seconds and sends them with a 10 second timeout.

- Any 2xx is success. Everything else, including timeouts and connection errors, is a failure.
- After a failure the next attempt waits 10 s, 30 s, 2 min, 10 min, 30 min, 1 h, 3 h, then 6 h, each plus up to 10 %
  jitter ([`WebhookBackoff`](../src/services/notifications/ClaimBridge.Notifications/Webhooks/WebhookBackoff.cs)).
  After nine attempts the delivery is `Abandoned`.
- Every attempt is logged with status code, duration and error. `GET /api/webhook-deliveries` and the portal's
  Integrations page show them; `POST /api/webhook-deliveries/{id}/redeliver` sends one again on demand, even for a
  disabled subscription.
- After 15 consecutive failures across deliveries the subscription is disabled through providers' internal API, and
  pending deliveries for it are abandoned. A provider admin re-enables it with `POST /api/webhooks/{id}/enable`.

All of these values live under `Webhooks` in the notifications
[`appsettings.json`](../src/services/notifications/ClaimBridge.Notifications/appsettings.json).

## Email

Denials and payer rejections also send a short email to the organisation's billing contact
([`EmailNotifier`](../src/services/notifications/ClaimBridge.Notifications/Email/EmailNotifier.cs)) with the claim
number and reason. Locally MailHog catches them at <http://localhost:8025>.

## Network

In Kubernetes notifications is one of two services allowed to call out of the cluster (the other is payers-gateway);
see the network policies in the [Helm chart](../deploy/helm/claim-bridge/templates/networkpolicy.yaml).
